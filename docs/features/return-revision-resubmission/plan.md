## Selected design and frozen implementation defaults

1. RETURN uses existing `POST /api/v1/approval-tasks/:id/decisions`, strict `{decision:"RETURN",reason,expectedVersion}` and UUID key. Trim using the existing decision schema. RETURN needs 1–4000 UTF-16 code units after trim; REJECT retains the approved 10–4000 new-write rule and historical replay compatibility. Return `201 DecisionResult`.
2. Under the existing request/cycle/stage/slot lock order, accept exactly one vote; close the cycle, mark the deciding slot RETURNED, cancel ACTIONABLE/WAITING sibling slots with version increments, and cancel remaining live stages. Preserve completed slots/stages. Create revision N+1 as a mutable copy of submitted revision N with fresh item IDs, the same pinned form, fields and exact amounts. Set workingRevisionId to the copy; retain submittedRevisionId and the closed currentCycleId until resubmission. Request becomes RETURNED with one version increment. Decision, lifecycle audit, outbox and replay completion commit together. Keep existing event names `DECISION_RETURN`, `REQUEST_RETURNED` and one decision outbox intent; do not duplicate effects on replay.
3. Creating the working copy at accepted RETURN makes PATCH immediately usable without introducing a new endpoint. Repeated saves edit only that copy; they never allocate further revision numbers. Revision N+1 becomes immutable at accepted resubmit and owns its distinct new cycle.
4. Resubmit reuses strict `submitRequestSchema` shape `{expectedVersion}`. Canonical path/key scope is distinct from submit. Canonicalization remains existing validated-body behavior: unknown fields/null version fail 422, expectedVersion is required, object field order is irrelevant. Persist original accepted response in the existing idempotency table within the transaction; replay lookup occurs before changed-state/version validation, after current identity and requester-role checks. No expiry/cleanup change is introduced.
5. Resubmit requires owner + current REQUESTER role + RETURNED + working revision + matching request version. Fully validate the original pinned form, including conditional applicability, line items, exact amounts and budgets. Allow disabled request type only for returned resubmission. Never compare returned form to the newly published form version. Resolve current published policy/assignment/budget under existing configuration publication gate and row locks; validate all required stage slots and no self-review.
6. Route against the original submitted department ID. Verify an active membership in that exact department and its current active department row; membership need not remain primary if the schema supports another active membership. New primary membership must not retarget the request. Missing original membership or inactive department returns existing `409 CONFIGURATION_INCOMPLETE` without writes. Preserve original departmentSnapshot byte-for-byte, even after department rename. Separate current routing eligibility from immutable historical display data.
7. Refactor only the shared submission persistence needed here: first submit allocates the official number once; resubmit reuses it and does not consume the number sequence. Preserve original request-level submittedAt as the initial submission timestamp; the new revision submittedAt/cycle createdAt carry the new submission time. Store current policy/assignments and current basic content in the new cycle snapshot, preserving prior snapshots. Append `REQUEST_RESUBMITTED` audit/outbox with new revision/cycle; expose `RESUBMIT` alongside `EDIT_DRAFT` on an authorized returned owner.
8. Metadata list default: direct JSON array plus existing `X-Pagination`; query pageNumber=1, pageSize=20, maximum pageSize=100/pageNumber=10000, strict unknown-query rejection. Include only submitted revisions ordered revisionNumber descending, ID ascending; exclude the mutable working copy. Metadata shape: `{id,revisionNumber,formDefinitionVersionId,submittedAt,submittedBy,cycleId}` with nonnull submission/cycle values. These list fields are implementation defaults under EP-039's unspecified metadata shape. Empty first draft returns `[]` with truthful zero counts; invalid bounds return 422.
9. Exact read returns frozen `RequestRevision` DTO, not current RequestDetail. Owner/current reviewer can read submitted revisions for that request. A former handler is entitled only if an actual immutable decision by that actor joins through slot/stage/cycle to the requested request and revision. Prior assignment/cancelled task alone is insufficient. Require current active identity; Administrator alone grants no content. Return indistinguishable 404 for foreign/missing/unsubmitted/mismatched records. Run authorization, total and projection under a coherent request read lock/transaction.
10. Preserve the stricter pinned metadata endpoint contract: non-admin `requestId` must pass current request-read authority. Do not broaden it for former handlers. Owner/current History renders configured labels from the authorized pinned definition. Historical task viewer uses exact RequestRevision values, line items and visible form-version ID; use field keys where configured labels are unavailable. It never fetches current detail, revisions list or definition endpoint. Obtain revisionId from the existing authorized handled ApprovalTask. This avoids a new endpoint or historical permission expansion.
11. History is read-only; no revision comparison. The owner can edit a returned working revision through the existing route. Lock type selection for returned work; show original number, department and form version, correction reason through permitted history, and explain that resubmit restarts review. Preserve safe inputs on 422/409/network/configuration failure; stale version requires explicit reload/reconfirmation. Retain stable keys for unchanged lost-response retries, including when the server already changed RETURNED to PENDING. Never persist private content/action keys to browser storage.
12. Existing #5 intentionally fails closed for completing a stage before unsupported stage-two activation. This issue must accept RETURN in either valid active stage without implementing unrelated stage-two APPROVE progression. Add a fixture with valid stage-two active context and completed prior stage. Preserve APPROVE/REJECT baseline behavior and test it.
