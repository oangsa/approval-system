# Request list and detail design — Issue #3

Status: planned, before implementation. Authority: [product requirements](../../specs/specifications.md) FR-005/006 and AC-005/006, [API](../../specs/api-specs.md) §§2–4 and 5.4, and [UI](../../specs/ui-specs.md) §§8–9. Frozen contracts prevail over this design. Issue #3 implements current list/detail; history, discussion, files, and decisions remain with their owners.

## Search and current detail

`POST /api/v1/requests/search` authenticates the current actor and applies requester ownership to both rows and count before client filters. Return a direct `RequestSummary[]`, JSON `X-Pagination` with currentPage, pageSize, totalPages, totalCount, hasPrevious, hasNext, and `Cache-Control: no-store`; expose the header to approved browser origins. Empty pages return an empty array and truthful metadata. Summary contains exactly id, requestNumber, typeId, typeCode, title, priority, status, requester, department, revisionNumber, currentCycleId, createdAt, updatedAt, submittedAt, version. Reuse shared Zod schemas and existing pagination; do not expose internal fields.

Search conditions combine with AND; allowed request number/title terms combine with OR. Allow status EQUAL/NOTEQUAL, typeId and priority EQUAL, createdAt/updatedAt/submittedAt date comparisons, submittedAt ISNULL/ISNOTNULL, and requestNumber/title EQUAL/CONTAINS/STARTWITH. Allow term names requestNumber, title, or both. Sort by updatedAt, createdAt, submittedAt, requestNumber or title in either direction; default updatedAt descending. Use UUID ascending as a stable tie-breaker and NULLS LAST for submittedAt. Default page 1, size 20, maximum 100; maximum 20 conditions and five term fields. Reject unknown fields, requesterId/id overrides, invalid operators, dates, blank terms and unsupported sort with 422. Bound text and use parameterized, escaped literal case-insensitive matching. Client criteria cannot widen ownership. An owner/sort index and migration are planned if justified; no data mutation or historical migration edits.

`GET /api/v1/requests/:id` reuses existing detail and pinned-definition reads. Owner or current authorized reviewer may read current persisted status and approved fields. Former reviewer, unrelated user, admin-only user and absent UUID receive indistinguishable safe 404; anonymous access receives 401. Recheck identity and authorization on every request. No administrator blanket access or historical-only current detail access.

## Interface and integration

`/requests` loads authenticated data on the client, with request-number/title search, status filter, sort and pagination. Desktop table and mobile cards show equivalent authorized rows and links; draft numbers have a human-readable fallback. Provide loading, empty, no-match, validation, unavailable and retry states. Preserve query state safely and suppress stale responses after query, route or identity changes. Clear private state on logout/account change; do not serialize private data into public SSR HTML.

`/requests/:id` keeps a persistent authorized header and four keyboard-accessible tabs: Overview, Approval, History, Discussion / Files. Overview uses the pinned submitted/working fields and current detail; Approval shows current stage and approver information from the DTO. History and Discussion / Files are honest integration-pending shells, without invented data or calls to unimplemented endpoints. No decision action or task link is inferred. Follow the styling contract, focus and reduced-motion requirements.

The presentation-only generic `RequestCollection<T>` receives `items`, `pagination`, `loading`, `error`, `onPageChange`, `renderDesktopRow(item)` and `renderMobileCard(item)`; stable row keys use resource UUIDs. Feature services own queries and authorization. Issue #4 consumes this interface with its own task DTO after interface handoff and #3 staging integration; it does not fork the primitive or change request DTOs. Serialize shared migration changes.
